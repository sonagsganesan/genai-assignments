Home Assignment – NoCode UI Automation

Functional LLM configuration in Settings, runtime execution integration, and plain-English test input.

Application: No-Code Automation PlatformTechnology: React, TypeScript, Express, Playwright and MCP

Introduction

No-Code UI Automation enables users to create and run browser-based tests without writing traditional automation code. Instead of manually developing Playwright or Selenium scripts, a user describes the required actions through a visual interface, a structured feature file, or plain-English instructions.

The platform translates these high-level test instructions into executable browser actions. It can navigate to web pages, enter data, click controls, validate expected results, retry failed scenarios, and collect evidence such as screenshots, videos, traces, and execution logs. This makes UI automation accessible to testers, business analysts, product owners, and other users who may not have programming experience.

In this project, Gherkin feature files and plain-English instructions are processed through the application and executed using Playwright with Model Context Protocol (MCP) support. An LLM assists with converting natural-language instructions, resolving UI elements, generating automation code, and healing failed locators. Browser and execution behavior can be controlled from the Settings page.

Executive summary

This assignment enhances an existing No-Code UI Automation platform in three areas. First, it documents and validates the configuration already available in the Settings module. Second, it replaces the static LLM information panel with a working configuration experience backed by secure server-side persistence. Third, it extends the editor so that users can submit natural-language test instructions in addition to Gherkin feature files.

The completed solution preserves the existing execution pipeline. Plain-English instructions are converted into Gherkin, and the resulting feature continues through the same parser, step mapper, Playwright/MCP browser controller, retry mechanism, and artifact collector. This approach adds a simpler authoring experience without duplicating the execution engine.

Assignment objectives

  1. Explore every option available in the Settings tab, including browser selection, headless execution, retry behavior, viewport settings, execution artifacts, appearance, and API configuration.
  2. Move operational LLM configuration from environment-only variables into the Settings UI and ensure that saved selections are used at runtime.
  3. Allow users to provide browser-test instructions in plain English while retaining support for existing Gherkin feature files.
  4. Provide an implementation report with examples, screenshots, output, verification details, and usage guidance.

Existing system assessment

The application already contained a React Settings page, a Zustand settings store, an Express/TypeScript backend, Playwright browser execution, MCP-based page interaction, Gherkin parsing, step mapping, retry utilities, and execution artifact collection. Browser and execution controls were functional, but the LLM section only displayed static or fallback information. The backend loaded provider credentials from .env, and the locator resolver initialized its client directly from environment variables.

The feature editor accepted only Gherkin. This meant that non-technical users still needed to understand Feature, Scenario, and step keywords before they could execute a test. The implementation therefore required coordinated frontend and backend changes rather than a visual-only update.

How the settings affect a run

The selected browser determines which Playwright engine is launched. Headless mode is appropriate for CI/CD and unattended execution, while headed mode is useful for demonstrations and troubleshooting. Viewport settings make it possible to exercise responsive desktop, tablet, and mobile layouts. Timeout and retry values define how long an action may wait and how many times a failed scenario may be attempted. Screenshot, video, and trace controls determine which diagnostic artifacts are collected.

Appearance and API preferences remain local browser preferences. In contrast, LLM settings are stored by the backend because provider credentials must not be placed in browser storage.

2. Functional LLM configuration

The previous static/read-only panel was replaced by an editable form. Save configuration sends the values to the backend; Test connection performs a small completion request against the selected provider.

Runtime flow: Settings UI → PUT /api/llm/config → protected backend JSON → client factory cache refresh → execution and locator resolver use the new provider/model.
  • Supported providers: OpenAI, Azure OpenAI, Anthropic and Groq.
  • The API key is written with restricted file permissions, excluded from Git and never returned to the UI. Only its final four characters are displayed.
  • Azure-specific controls appear only for Azure OpenAI.
  • Validation rejects unsupported providers, missing required fields and invalid token/temperature ranges.

Persistence and runtime activation

The backend loads environment settings as an initial fallback and then applies any saved runtime configuration. Saving the form writes the selected values to config/llm-settings.json, updates the live application configuration, and clears cached LLM clients. New conversion and execution requests therefore use the latest settings without requiring a server restart.

The locator resolver refreshes its LLM client before resolution operations. This closes the original gap where locator resolution continued reading .env even after another part of the application had changed configuration.

Security considerations

  • The runtime settings file is excluded from source control.
  • The API key is never included in the configuration response.
  • The UI shows only a masked suffix so users can identify which credential is saved.
  • The saved file is created with restrictive permissions where the operating system supports them.
  • Provider validation is performed on the server instead of relying only on client-side controls.

3. Plain-English input

The editor now supports two modes: Gherkin and Plain English. On Run, plain instructions are converted to valid Gherkin using the saved LLM configuration. The generated Gherkin is placed back in the editor and sent through the existing parser, mapper and Playwright/MCP execution path.

Processing workflow

  1. The user selects Plain English in the Test Instruction Editor.
  2. The user enters an ordered description of the browser actions and clicks Run.
  3. The frontend calls POST /api/llm/convert-instructions with the instruction text.
  4. The backend uses the active provider and a controlled system prompt to request Gherkin-only output.
  5. Markdown fences are removed and the response is checked for both Feature: and Scenario:.
  6. The generated content replaces the editor content and becomes visible for review.
  7. The existing execution request receives the generated Gherkin along with base URL, browser, retry, timeout, and artifact options.
  8. The normal parser, mapper, Playwright/MCP automation, and results workflow continues unchanged.

Expected execution behavior

The generated feature is not executed through a separate or simplified automation path. It is treated exactly like an uploaded or manually authored feature file. Consequently, browser selection, headless mode, viewport, retries, screenshots, video, tracing, step mapping, locator resolution, and failure handling all continue to apply.

6. User guide

Configure the LLM

  1. Start the backend and web application.
  2. Open Settings → LLM.
  3. Select a provider and model.
  4. Enter the API key and any provider-specific fields.
  5. Choose max tokens and temperature.
  6. Click Save configuration.
  7. Use Test connection to validate the provider setup.

Run a Gherkin feature

  1. Open the Test Instruction Editor.
  2. Select Gherkin.
  3. Write or import a feature.
  4. Review syntax and step mappings.
  5. Click Run and select the desired execution options.

Run plain-English instructions

  1. Open the Test Instruction Editor and select Plain English.
  2. Describe the actions in their intended order and include exact labels or values where possible.
  3. Click Run.
  4. The configured LLM converts the instructions and the editor shows the generated Gherkin.
  5. The application starts execution with the selected browser and execution settings.

7. Verification

  • Backend TypeScript compilation completed successfully.
  • Frontend TypeScript compilation and Vite production build completed successfully.
  • The Settings page displays Chromium, Firefox, and WebKit browser options.
  • Headless/headed execution, viewport, timeout, retry, screenshot, video, and trace controls are available.
  • LLM configuration can be saved through the Settings page and applied to new executions without restarting the server.
  • Saved API keys are masked in API responses and are not returned to the browser.
  • Provider-specific validation is applied, including the required endpoint and deployment fields for Azure OpenAI.
  • The LLM connection test reports success or a clear provider error from the Settings page.
  • The editor supports switching between Gherkin and Plain English input modes.
  • Plain-English instructions are converted to Gherkin before entering the existing Playwright/MCP execution flow.
  • The generated Gherkin is displayed in the editor so it can be reviewed before subsequent execution.

8. Error handling and edge cases

  • Plain-English conversion is rejected when the instruction field is empty.
  • A clear service error is returned when plain-English mode is used before an LLM API key is configured.
  • Invalid provider, model, token, or temperature values are rejected before persistence.
  • Azure OpenAI configuration is rejected when its endpoint or deployment name is missing.
  • If a new API-key field is left blank, the existing saved key is retained instead of overwritten.
  • Conversion output is checked for the required Gherkin structure before execution.
  • Provider errors are passed back as actionable UI messages during connection testing.

Conclusion

The assignment delivers an accessible authoring experience without replacing the proven execution pipeline. Users can still work directly with Gherkin when they need precision, while less technical users can describe the same workflow in plain English. The functional Settings implementation makes provider selection explicit, keeps secrets on the backend, and ensures the chosen model participates in actual conversion and locator-resolution work.

The result is a more usable No-Code UI Automation platform with configurable browsers, execution controls, runtime LLM integration, natural-language authoring, reviewable generated output, and portable documentation containing embedded screenshots.
