Swagger AI Agent

Contract-driven API verification with screenshots and test scenarios

Objective. Demonstrate how an OpenAPI specification becomes a selected set of API checks, an execution report, and a reusable Playwright test suite.

System under testIncluded Customer API on 127.0.0.1:8081, authenticated with a bearer token.
Agent workspaceReact user interface and Express API on 127.0.0.1:3000.
InputsOpenAPI document, selected operations, environment URL, credentials, and test options.
OutputsRun plan, request and response evidence, pass/fail totals, and generated Playwright tests.

Workflow at a glance

Import specification → select endpoint → configure target → plan checks → run → inspect evidence → generate suite.

Evidence used in this assignment

The screenshots were captured from the running application with the included demo API. The browser check uses a free local port, so its screenshots show a different port from the manual quick start. The passing and invalid-token scenarios were exercised through the browser workflow. Additional scenarios on the final page are acceptance cases with expected outcomes.

Scenario 01 · Import

Load the API contract

The import screen accepts pasted JSON or YAML, a specification URL, or an uploaded file. The demo document defines GET /customers/{id} and its expected 200 response.

Steps and expected result

  1. Start the demo API and agent service.
  2. Open http://127.0.0.1:3000/ui/.
  3. Keep the sample YAML and select Import specification.
  4. Confirm the operation explorer lists getCustomer.

Choose the target and plan

Scenario 03 · Positive execution

Run with valid credentials

With the demo bearer token, GET /customers/123 returns 200. The report shows the expected status, request URL, redacted authorization header, response body, and duration.

InputExpectedObserved
Valid bearer token; customer ID 123HTTP 200 and a passed checkHTTP 200; report shows 1 passed and 0 failed

Scenario 04 · Negative execution

Detect invalid authentication

Change the environment token to invalid-token, save the environment, and run the same operation. The target returns 401 while the selected happy-path check expects 200; the report flags the mismatch.

InputExpectedObserved
Invalid bearer token; customer ID 123Happy-path check fails and shows the actual 401 responseReport shows 1 failed; request and response evidence is available

After this test, restore demo-token. The browser workflow confirms the next run passes again.

Scenario 05 · Test generation

Export reusable automation

The selected operation can be converted into a Playwright API test file. The preview includes the request, expected status, and environment variable use. The browser offers a download; the REST export endpoint provides a package manifest and config too.

Run requirement: set TEST_BASE_URL and, for this demo, TEST_BEARER_TOKEN. Review generated IDs and payloads before running write operations.

Conclusion

The demonstrated flow traces a contract operation through planning, an actual HTTP call, a report, and generated automation. The failed-token case shows that the report retains the information needed to investigate a mismatch. The agent stores data in memory, so a production deployment would need persistent storage and operational hardening.
